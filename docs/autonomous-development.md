# 自律開発フロー

この文書は、Codex / ChatGPTが「察して。」を継続的に改善し、公開品質へ近づける標準ループと安全境界を定義します。

## 目的

ユーザーが毎回、実装できる粒度まで仕様を書かなくても、次の循環をAI側で進めます。

ユーザーの目的・感想 → 現状分析 → 公開品質の未達確認 → 改善候補 → 仮説 → 小さな実装 → 自動検査 → 評価 → 人間確認 → main反映 → 次の改善

ユーザーの主な役割は、方向性、好み、OK / NG、時々の実機感想です。

## AI Game Director v1

自律改善は同じモデルが担当しても、Director / Reviewer / Engineer / Evaluator の判断段階を分離します。

### Director

- 最新main、open PR、`docs/release-readiness.md` を読む。
- 公開品質への改善余地を最大3件挙げる。
- 影響範囲、期待効果、回帰リスクを比較し、1件だけ選ぶ。

### Reviewer

- `docs/evaluation-rubric.md` と公開品質ゲートに沿って現状を評価する。
- 問題、仮説、成功条件、回帰条件を実装前に明示する。

### Engineer

- 1サイクル1目的を守る。
- 必要最小限の変更とテストを行う。
- 高リスク領域へ踏み込まない。

### Evaluator

- 変更前後を同じ基準で比較する。
- `typecheck` / `test` / `build` を通す。
- 改善と合理的に判断できない変更は残さない。

## 実行方法

`.github/workflows/ai-game-director.yml` が実行正本です。

### 手動 analyze

コードを変更せず、改善候補と仮説だけを出します。

### 手動 implement

1件だけ実装します。安全ゲートを通った候補は専用ブランチへ保存し、**Draft PRを自動作成します。mainへは自動反映しません。**

### 定期実行

**Phase 1では定期実行しません。**

2026-08-16に、定期実行が短時間に多数走り、APIクレジットを消費した一方で、人間のVisualレビューを通していないコード描画の場面がmainへ入る問題が確認されました。このため、自律改善は再び手動起動 + Draft PR + Preview確認へ戻します。

将来、定期実行を再開する場合は、少なくとも次を満たしてから別PRで明示的に有効化します。

- API利用頻度と上限を事前に決める。
- Visual / Art変更を自動公開対象から除外する。
- Draft PRまたは同等の人間確認経路を維持する。
- 同じ失敗を繰り返さない品質ゲートが自動テストで固定されている。

## Visual / Artの安全境界

プレイヤーが見る場面の絵は、コードテストだけでは品質判定できません。

- CSS / HTML / SVGの丸・矩形・疑似要素等で人物や背景を組み立てた仮絵を、本番アートとして採用しない。
- 人間が目視合格したローカル画像アセットがない場面を、Game Directorが文章選択から画像内操作へ自動昇格させない。
- Visual変更は通常のChatGPT / Codex作業として別PRで扱い、Cloudflare PreviewをAndroidで確認する。
- Image APIを使う場合も、生成回数・品質基準・採用素材を人間確認し、失敗素材を反復生成してコストを消費しない。

Game Directorの安全ゲートでは、SceneArtwork、PlayroomScene、styles、scene assets、prototypes等のVisual制作領域を変更禁止にします。

## 自動マージについて

Phase 1ではAI Game Directorからmainへ自動マージしません。`typecheck`、`test`、`build` が成功しても、Draft PRを経由します。

将来の自動マージ再導入は、Visual変更を含まない十分に限定された低リスク範囲で、別途ユーザー承認を得てから行います。

## 人間承認を残す領域

- Secret / API key / 権限
- 課金・広告
- 個人情報・ユーザーデータ保存
- 外部データ送信
- 子ども向け安全設計の緩和
- 大規模なゲーム目的・世界観変更
- 高額または反復的な画像/API利用
- Visual / Artの採用判断
- デプロイ基盤やworkflowの破壊的変更

## 公開品質への成長

AIは単に機能を増やすのではなく `docs/release-readiness.md` の未達を減らします。

優先順位は原則として次です。

1. ゲームが最後まで正常に遊べる
2. 初見理解と操作感
3. 結果・スコア・リプレイ性
4. スマホ安定性
5. 年代別モードとコンテンツ量
6. 子ども向け品質
7. 細かな演出・磨き込み

公開判定は `NOT_READY` / `PREVIEW_READY` / `PUBLIC_READY` の3段階で扱います。

## 問題生成ループ

ゲーム本体の改善とシチュエーション生成は分離します。問題生成は少量バッチで行い、年代適合、重複、迷いの質、安全性、操作可能性を確認してから採用します。

## ユーザーが介入したとき

ユーザーの最新の明示指示を最優先します。「これは違う」「この方向にしたい」「ここは触らないで」といったフィードバックは、次回以降の自律改善ルール・優先順位へ反映します。
